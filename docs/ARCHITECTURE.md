# Architecture

How the repository is organised, and why. The product rules (Global-only data, no ranked data, nothing invented) are in the README and in `docs/DECISIONS.md`; this file is about the code.

## The layout at a glance

Two folders hold the code, `src/` (what the application is, and everything that checks it) and `scripts/` (what you run by hand). A test sits next to the code it checks: `x.js` and `x.test.js` (node:test, against a real MySQL), `x.e2e.mjs` (a Playwright script, run by `src/testing/run-e2e.mjs`).

| Folder              | What it holds |
| ------------------- | ------------- |
| `src/server/`       | The Express 5 application (ES modules, MySQL). |
| `src/client/`       | The browser application: vanilla JavaScript modules and CSS, no framework. |
| `src/shared/`       | Code that runs in both places: translation runtime, route table, media helpers, build, draft, combo and reflex models, the stat kinds and their value levels (`stat-values.js`), conditions, hero name keys. |
| `src/public/`       | Files served as they are: fonts, icons, logo, social image, and the generated `locales/`. |
| `src/translations/` | The translation sources. The English text is the key. `src/public/locales/` is generated from them. |
| `src/testing/`      | What the tests share: the test application and its database, the layout lint, the source collector, `run-e2e.mjs`. |
| `scripts/`          | Command-line tools, one folder per purpose: `build`, `i18n`, `accounts`, `database`, `data`, `performance`, `catalog`, `brand` (the mark and the files made from it), `dev` (the demo world, access matrix, page pictures, the audit of the checklists), `vod-drafts` (the Python pipeline that reads broadcasts). Their tests sit next to them. |
| `docs/`             | Decisions, report, security notes, set-up guides. |
| `dist/`             | The output of `npm run build`. Ignored by git. |

Outside these, only the project files: `package.json`, `Dockerfile`, the compose files, the linter settings, `README.md` and `deploy.md`.

## The server

```
src/server/
  server.js         process entry: config, database, listen, graceful shutdown
  app.js            composition root: builds the Express app from a store and a config
  config.js         every environment setting (no secret has a built-in default)
  platform/         plumbing shared by every feature, no product rules
  features/<name>/  one vertical slice per area of the product
```

`app.js` touches neither the network nor the process: the caller hands it the store, the config and the synchronisers. That is what lets the tests build a complete app around a throw-away database.

### `platform/`

| Folder or file              | Role                                                                                                                                                                                                    |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `http/web-root.js`          | Where the web folders are (`WEB`: client, shared, public, dist).                                                                                                                                        |
| `http/assets.js`            | Serves the bundle (immutable, with the brotli and gzip copies the build made), shared modules, static files and, without a build, the client sources. No `Vary` on any file.                            |
| `http/cache-control.js`     | What a browser or a CDN may keep of a response: `sameForEveryone`, `publicFor`, `revalidate`; called only once the answer is good.                                                                      |
| `http/page-handler.js`             | The HTML shell: fills the template, inlines the critical CSS (and, for a page drawn, the sheets of its first screen), computes the CSP hashes, picks the language and the pre-render.                   |
| `http/prerender.js`         | Draws the first screen of public pages once in headless Chromium and caches it, so visitors receive a page already drawn.                                                                               |
| `http/first-paint.js`              | The small constant script that loads everything else after the first paint.                                                                                                                             |
| `http/security-headers.js`          | Security headers, Content-Security-Policy, cross-site request check.                                                                                                                                    |
| `http/identity.js`          | Cookie identity: a Google user or an anonymous guest.                                                                                                                                                   |
| `http/rate-limits.js`       | One limiter per kind of request.                                                                                                                                                                        |
| `http/async.js`             | `wrap` (async handlers), `requireAdmin`, `adminOnly`, `requireGoogleUser`.                                                                                                                              |
| `database/store.js`         | Composes per-feature stores into one `store` and owns pool (size from `DB_POOL_SIZE`…), `ping`, `runExclusive` (a job that one instance at a time may run, by MySQL advisory lock) and `closeDatabase`. |
| `cache.js`                  | In-memory TTL cache: least recently used out past a limit, one computation for simultaneous askers, failures not kept, `clear()` also drops what is being computed.                                     |
| `database/migrations/`      | Numbered, additive, idempotent migrations (`001` … `039`).                                                                                                                                              |
| `security/`                 | Password hashing, TOTP, the secret box that encrypts seeds, key loading.                                                                                                                                |
| `images/`                   | Avatar, catalog image and map image processing (sharp).                                                                                                                                                 |
| `errors.js`                 | Typed errors; every message is an English template plus values, translated when it reaches the client.                                                                                                  |
| `validation.js`             | Generic request parsers (text, integer, uuid, pagination, …). Feature-specific parsers live in the feature.                                                                                             |
| `i18n.js`                   | Server-side translations and language negotiation.                                                                                                                                                      |
| `logger.js`, `lifecycle.js` | JSON-lines logger with redaction; graceful shutdown.                                                                                                                                                    |

### The public API (`features/api-keys/`)

A signed-in person makes **API keys** (Settings): `hok_` + 43 characters, only the SHA-256 kept (`api_keys`, migration 033), scopes, an expiry, revocation at once. `gateway.js` serves `/api/v1`: it checks the key (the same refusal for an unknown, revoked or expired key), counts each refusal against the address, limits the key itself, allows **GET only**, matches the address against the allow-list of `endpoints.js` and its scope, then hands the request to the **same router** the application uses, as the owner of the key and with no administrator or editor right. So the API shows exactly what the application shows to the same person, and the two cannot drift apart. `routes.js` makes, lists and revokes keys with the browser session only. See [API.md](API.md).

A series can be put on a **team** (`team_series`, migration 034) by its creator when they lead the team (owner, manager, coach); the members then read it as viewers (`series/series-store.js`: the visibility is "owned, given, or on a team of mine").

### `features/<name>/`

A feature is a vertical slice. The files it has depend on what it needs, and each has one job:

| File            | Job                                                                                                                        |
| --------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `routes.js`     | HTTP only: parse the request, call the store and the domain, send JSON. `createXRouter({ store, limiters, … })`.           |
| `store.js`      | SQL only. `createXStore({ pool, inTransaction })` returns the feature's methods; `platform/database/store.js` merges them. |
| `domain.js`     | Pure rules and parsers: no I/O, so the routes, the stores and the tests share them.                                        |
| `validation.js` | Parsers of this feature's request bodies and queries, built on `platform/validation.js`.                                   |

The features: `auth`, `catalog`, `combos`, `community`, `discord`, `export`, `heroes` (with `sync/`), `media`, `preferences`, `reflex`, `series`, `sharing`, `space`, `stats`, `teams`, `tier-lists` (with the official ratings), `tournaments` (with the popular drafts and heroes), `training`, `translations`.

The **catalog** is the one that grew most files. `domain.js` parses what an administrator writes (a stat and its options, a stat line that is a value or the option of a choice stat, temporary or not and conditional, an item, an arcana, a hero's base stats); `fields.js` holds the small checks every body is read with (text, number, whole number, flag, object); `conditions.js` is the server side of `src/shared/condition-model.js` (the same rules, plus the checks of what the page cannot be trusted with: the stat, the tag, the hero must exist, a hero list holds at most 20 entries, depth and size are bounded); `usage.js` says where a stat, an option or a tag is used (an item, an arcana, a hero profile, a condition) so that deleting it or changing its kind is refused with a 409 that says how many places use it. A condition is **data**: it is stored as JSON, read back by the parser and walked by `evaluate()`, and nothing is ever run from it.

An item is sorted two ways, and the code keeps the two apart: its **slot** (`category`: `boots`, `regular`, `utility`, `late`, with `GROUP_OF` and `SLOTS` in `src/shared/build-model.js`, what a build has room for) and its **shop category** (`shopCategory`: one of `SHOP_CATEGORIES`, or none; the column `shop_category` of migration 028). `domain.js` has `slotOf` and `shopCategoryOf` (the second returns `undefined` when a body does not say, so an older page that does not know the field leaves it as it was) and `parseItemSort` (the body of `POST /api/admin/catalog/items/bulk`); `store.js` has `sortItems` (one transaction, all or none) and refuses a change of slot for an item that a recommended build uses (`refuseSlotChange`, the same rule on a single edit). The cache of `readCatalog` carries a generation number: a read that started before a write is not kept, so a page that reads right after saving never gets the old catalogue (`src/server/features/catalog/catalog-cache.test.js`).

The pictures are processed once, at upload, by `platform/images/catalog-image.js` (`processCatalogImage`: up to 256 px, WebP, an arcana drawn small made 128 px) and cut to the size a page asks for when it is asked (`catalogImageVariant`, the widths in `CATALOG_IMAGE_WIDTHS`, a small in-memory cache `createVariantCache`; `/catalog-images/:id?w=`). The importer `scripts/catalog/import-images.mjs` goes through the same functions as the page (`processCatalogImage`, `parseItem`, `parseArcana`, the store), so what it creates is what the page would have created; its pure rules (names, slot, colour of an arcana) are in `scripts/catalog/naming.mjs`.

The **translations** feature (`src/server/features/translations/`) translates what the staff writes, in the background, and nothing else. It is split like this: `domain.js` (pure: the key of a text, the numbers of a text, what a translation must be, the daily budget, the backoff), `sources.js` (reads every text the staff wrote out of the catalog, the hero profiles, the builds, the combos, the situations and the maps, and says what kind each is), `store.js` (the three tables of migration 027), `service.js` (the translator: a round syncs the texts, asks the provider for what waits, checks and writes, under a MySQL lock so that only one process does it), `providers/` (`anthropic`, `deepl`, `libretranslate` behind one `translate({ items, languages })`, and `http.js`, which turns a failure into an `auth`, `rate`, `unavailable`, `bad-answer` or `bad-request` error) and `routes.js` (the public dictionary and the administrators' routes). The service is created in `server.js` (and `src/testing/test-app.js`) and handed to `createApp`; it starts its timers only when `start()` is called, so a test drives a round with `sweep()`. The app calls `kick()` after any successful write to a path that holds staff texts (`CONTENT_WRITES` in `app.js`), so a new text is translated a moment after it is saved.

What the translator sends, and for which languages, is decided in three places. **Languages**: a language is translated only once somebody asked for it (`translation_languages`, migration 029: the dictionary route calls `want(language)` when a visitor reads the site in it, an administrator can ask for one or for all of them, and a text kept as typed, `content_texts.kept`, stays as typed in a language asked for later). **Quota**: a provider that can say what its account has left (`usage()`: DeepL's `GET /v2/usage`) gives the translator an allowance, `allowanceOf` in `domain.js` (90 % of the limit minus what is used; no limit when the account has none), and the translator stops before a batch that does not fit; a provider that cannot say is held to a daily number instead (`TRANSLATION_DAILY_CHARS`, 400 000 by default). **Requests**: a provider can say how many texts and characters it takes in one request (`limits`), and `providers/each-language.js` asks the first language alone (its answer says which language each text is written in) and the others a few at a time, keeping what was done when the service stops half-way (`results.done`, `results.interrupted`). `providers/deepl.js` is the one the owner uses (50 texts a request, a context about the game that is not billed, `usage()`, `languages()`); `providers/http.js` maps 456 to `quota`, 429 to `rate`, 401 and 403 to `auth`.

The training area is spread over three of them, which meet only through the composed `store`: `training` (the heroes a person works on, the notebook with its video reviews, the maps and the situations), `combos` (the combos the editors write, what each player acquired, the spaced-repetition schedule `combo_reviews`, the hero goals of a team) and `reflex` (the runs, the goals of a team, its ranking and its settings, the routes that put a team's training together: `GET /api/teams/:id/training`, `GET /api/training/assigned`). What a routine, a ranking or a review schedule means is in a `domain.js` (pure, tested without a database); the page of a team reads the goals about reflexes and about heroes in the one answer.

Who may write what is decided in one place, `src/shared/access-rules.js`: the **editors** are the administrators and the people with the `contributor` label; `requireEditor` (in `platform/http/async.js`) is what the editor routes call (`/api/builds`, `/api/combos`, `/api/official-tiers`; the `/api/admin/*` prefix is for administrators only, which is why those routes are not under it).

A feature may use another feature's `domain.js` (for example `heroes/hero-domain.js` is read by `series` and `tournaments`) but never reaches into its store: stores talk to each other only through the composed `store`.

### The draft rules

The order of the actions, the pick-only orders and the rules about which heroes are still free exist once, in `src/shared/draft-model.js`. The server (`features/series/draft.js`) and the browser import the same functions, so the two can never disagree.

## The browser application

```
src/client/
  index.html        the shell template; the server fills its __PLACEHOLDERS__ and {{t:…}} keys
  main.js           entry point: loads the language, installs every feature, starts the router
  app/              start-up and plumbing (state, router, api client, actions, i18n, hydration, lazy loading of the heavy pages)
  lib/              helpers with no game rule (DOM, formats, skeletons)
  domain/           labels and display rules of the game (lanes, catalogue display, hero of the day, vod links...)
  shell/            top bar, navigation menu, account menu
  features/<name>/  one folder per area; a feature exports `install…()` and its view functions
  styles/           critical.css, main.css and the partials it imports
```

- **State.** One shared, mutable `state` object (`app/app-state.js`). Views read it; handlers change it and call `render()`.
- **Events.** `app/event-actions.js` is a registry: a feature registers `onAction("data-action-name", handler)`, `onClick(selector, handler)`, `onChange`, `onSubmit` or `onInput`. `installActions()` attaches the four listeners once, on `#view`, and turns a handler error into a toast. No feature has its own giant listener.
- **Features install themselves.** `main.js` calls each feature's `install…()` once; nothing else in `main.js` knows what the feature does. The exception is the heavy areas (heroes, scrims and the draft board, history, home, tier lists): each has a page module (`features/<area>/…-page.js`, `createXxxPage()`) that installs the area's listeners the first time the page is loaded, and `app/lazy-actions.js` lists the `data-action` names each one registers, so that a button of such an area works even before its page is there (`onLazyActions` in `app/event-actions.js` loads the page, then hands the click to the real handler). `app/lazy-actions.test.js` checks that the table says exactly what the files register and that no name is taken twice.
- **Lazy loading.** Heavy screens (hero editor, build lab, catalog, teams, heroes, scrims, history, home, tier lists…) are loaded on first use through `app/lazy-pages.js` (a loader has `.ready()`: the built page once it is there, so a page already loaded is drawn at once), so the first bundle stays small (63 KB of JavaScript on every page, 23 KB compressed). The page handler asks the browser to fetch the chunk of the page of the view it serves together with the HTML (`src/shared/view-registry.js` says which module draws which view, `scripts/build/build.mjs` finds its chunk, the manifest's `pages`, `http/page-handler.js` writes it in the boot block), instead of after the main script has found out which page it must draw; `src/shared/view-modules.test.js` fails when a page loaded on demand is not in that map.
- **Hydration.** For an anonymous visitor the server sends the first screen already drawn; `app/hydration.js` reconciles it with the first client render instead of replacing it, so the painted elements stay the same nodes. A page the server drew has `class="ssr-first"` on `<html>` (no entrance animations on that first load, so its text is on the screen at the first paint; `components/motion.css`), which the client removes 2.5 s later.
- **What a page needs, loaded once, in one wave.** `src/shared/view-registry.js` says what each view reads (always the heroes; the series for the scrims, live, history and player views; the tier lists for the tier lists), `app/roster-data.js` loads only that (`startData(names)` as soon as the route is known, `dataFor(view)` to wait for it, `dataLoaded(view)` to know it is there; a load that failed is tried again by the next page), and `app/router.js` does not draw a view whose data is not there. The session of a person who is signed in, their preferences and the counters of the menu do not cost a request: the server writes them in the `b` of the boot block (`http/client-bootstrap.js`, `features/auth/session-view.js`, a response that is `private, no-store`) and `app/stylesheet-loading.js` hands them out once (`takeBootstrap`). A page the server does not draw starts, like the others, with the constant boot loader (`http/first-paint.js`), which waits for the first paint and then starts everything: static `preload` / `modulepreload` tags in the head were tried and removed (they compete with the first paint: the simulated first paint went from 0.8 s to 2.2 s), see DECISIONS, revision 30.
- **Frames: the first screen of a person who is signed in.** For a view of `FRAME_VIEWS` (and, for a visitor who has a link with a token, `VISITOR_FRAME_VIEWS`) the server sends the _frame_ of the page: its title, its introduction and a skeleton, the same for everybody. It is made like the pages of visitors (`http/prerender.js`): the real client runs in headless Chromium as a made-up person (`user`, `staff` for an administrator or an editor, `visitor`), every request of the person is answered with an empty list and every request of the page is held, and the capture is taken as soon as the page has a heading. The response is `private, no-store`, has `data-ssr="frame"`, the first-paint pack of the view (the same `first-paint.json`) and the whole stylesheet prefetched. In the browser a page calls `pageRoot(app, hydration).paintFrame(html)` to draw the frame itself when it was not sent (a page reached by a link inside the application), and its next drawing is _reconciled_ with it (`app/view-wrapper.js`): the title is the same node from the first to the last paint, so the largest paint is early and nothing moves. A page has a frame when someone has looked at it (`src/client/frames.e2e.mjs`: same heading before and after, the style of the pack, no JavaScript, both themes, and the frame of each kind of person); the series (except one whose game is being drafted: the next point), the invitation links (`?join`, `?invite`, `?next`) and the pages that need what their address says (an exercise, a situation, a hero of the guides) have none. The training area has four (`TRAINING_PATHS`), drawn by `features/training/pages.js` with the same `zoneHead(zone)` as the zones themselves, so that the two cannot say different things.
- **Language.** `app/language-start.js` awaits the catalog of the page's language before any other module runs.
- **Pictures and categories.** `domain/catalog-display.js` writes the `src` and `srcset` of a catalogue picture for the size it is drawn (64, 128 or 256 px wide, the next size up for a sharp screen); `domain/catalog-display.js` has the names of the shop categories. The Catalog page sorts items in bulk (a panel under the filters, the lines turn into boxes to tick, the panel is refreshed in place so the list keeps its scroll) and the build lab narrows the items down with chips under the groups of slots.
- **The order of the pieces.** One rule per kind of piece, in `src/shared/build-model.js`: `compareArcana` (by colour in the order of `ARCANA_COLORS`, red, blue, green, then by name) and `compareItems(shopCategory)` (by name, except the Roaming items, which go by type first, `ROAMING_TYPES`: Guardian, then Crimson Shadow, then by name). The server lists the arcana in that order (`readCatalog`, `ORDER BY FIELD(color, …), name`), so the API and every page start from it; `domain/catalog-display.js` applies the same rule to the names as the visitor reads them (the staff's translations) in the alphabet of their language, in the pages of the game data and the picker of the build lab; `src/shared/piece-order.test.js` ties the server's order to the shared rule.
- **What the staff wrote.** `domain/staff-content.js` loads the dictionary of the visitor's language once (`GET /api/content-translations?lang=`, revalidated with an ETag) and `tx(text)` returns the translation, or the text itself when there is none. The pages that draw a text of the staff (a stat, an option, an item, a note, a build, a combo, a situation) wrap it in `tx()`; the routes of those pages wait for `contentReady()` before drawing. The editors never use it: they show and save the text as it was typed, so a translation can never be written back. `domain/condition-text.js` writes a condition in words (`describeWhen`), through `tx()` for the names it contains.
- **The room of the draft (frame).** A signed-in person who opens a series whose game is in progress, or `/live`, receives the room drawn (`ROOM_FRAME_PATH`, pack `scrims-room`): the band of the series, the two sides and the clock, empty and `inert`. The server first checks that the series is the person's and in progress (`draftInProgress`, `http/page-handler.js`), otherwise it sends the ordinary page. The markup is one function (`roomMarkup` in `features/draft/draft-room-markup.js`) used by the frame and by the real board, so they cannot differ; the real board takes the room over (`mount` adopts the existing `[data-ref="area"]`), and the clock is the same node. Checked in `src/client/frames.e2e.mjs`.
- **Quiet mode.** While a reflex exercise runs (`features/training/reflex/exercises/frame.js` → `app/app-state.js`), `state.quiet` is true and `<html>` has `is-quiet`: the shell's periodic refresh of the badges does not run, the background video is neither fetched nor played (`features/heroes/background.js` listens to `hok:quiet`), and the animations that never end are paused. An exercise itself never imports `app/api-client.js` or calls `fetch`: a test reads its source to prove it. The result is the only request, sent by the page once the run is over.
- **The screen of a run.** An exercise is not drawn in the page: while it runs, `.is-running .rx-board` covers the whole window (the top bar and the tab bar included, the page behind does not scroll: `html:has(.is-running)`), with a bar (the way out, the name, `hud.js`: a counter, lives, a thin progress bar) and the stage of the exercise. That screen is dark in both themes (`keep-dark`): the pads, the balls and the targets are drawn for that ground, and the light theme has nothing to redo for eight exercises. An exercise gets `hud` with the others (`stage`, `finish`, `random`) and only says numbers (`progress`, `count`, `lives`); the words of the run stay in `.rx-status`, the line that is read aloud. Escape stops a run.
- **Waiting and typing.** `lib/skeleton.js` draws placeholders (rows, cards, a page head) shaped like what is coming, always behind the `loading-line` bar that hydration and the pre-renderer look for; `lib/debounce.js` waits for a pause in typing (the catalogue filter and the hero search: one letter costs 49 and 27 ms on a slow processor).

### Styles

- `critical.css` is inlined in every page (allowed by a CSP hash). It draws the shell and the first screen.
- **The first paint of a page the server draws.** Such a page arrives with its stylesheet inline, but not the whole one (every page has a sheet of its own: the full stylesheet is several hundred KB): `critical.css` + the partials its first screen is drawn with, listed in `src/client/styles/first-paint.json` (`always` for the shared ones, then per view the sheets of that view), in the cascade order of `main.css`. `scripts/build/build.mjs` makes one minified pack per view (`dist/first-paint/`), `http/page-handler.js` inlines it and allows it by its own hash (a `Content-Security-Policy` of that response; the static one only knows the critical sheet), and the boot script loads the whole stylesheet right after the first paint, like for the pages the server does not draw (hydration waits for it). A new page sheet needs no entry unless a view the server draws uses it; `src/client/styles/first-paint.e2e.mjs` compares the computed style of every element of each drawn page with the subset and with the whole stylesheet (both themes, a phone, a right-to-left language) and names what is missing, and `src/server/platform/http/ssr.test.js` checks that every drawn view has an entry made of real partials.
- `main.css` is only a list of `@import`s, in cascade order (the order is the cascade: do not reorder). The styles are one design system: `base/` (tokens, reset, accessibility), `components/` (buttons, forms, cards, tabs, media, data, overlays, pickers, build, motion, …), `shell/` (top bar, navigation, palette, background) and `pages/` (one sheet per page). Colours, radii, type and easing are custom properties of `base/tokens.css`; the light theme only moves the neutral tokens. A page sheet styles its own blocks and nothing else; what two pages share lives in `components/`.
- **One board for the tier lists and the official ratings.** The coloured label of each tier and the round portraits of its heroes are `components/tier-board.css`, drawn by `domain/tier-labels.js` (`tierRow`, `tierPortrait`); the colour of a row follows the name of its tier (`data-tier`, from `src/shared/tier-names.js`), the same colours as the rating of a hero, and a tier with another name takes the colour of its place. The two pages only differ in what can be done on the board; `src/server/features/tier-lists/tiers.test.js` fails if one of them draws its own rows again.
- The client never writes a `style` attribute (the CSP forbids it): sizes and hues are classes (`s-48`, `ls-34`, `hue-3`, `d-2`), and values that come from data travel as `data-p` and are written through the style object (`lib/dom.js`).
- `esbuild` bundles and minifies the partials into one file at build time; without a build the server resolves the imports itself (`readStylesheet`).

## Build and serving

- `npm run build` bundles `src/client/main.js` (code-split) and the stylesheet into `dist/` with content hashes and writes `dist/manifest.json`. Built mode is used whenever the manifest exists.
- The build also writes a brotli (level 11) and a gzip (level 9) copy next to every script and style of `dist/`; `http/assets.js` hands them out as they are (brotli first, whatever the order of the visitor's header).
- Without a manifest (development, tests) the server serves the sources of `src/client/` directly. `HOK_SOURCE_ASSETS=true` forces that, and the tests set it so a stale build can never hide a change; `HOK_TEST_BUILT=true` makes the tests run against the bundle instead.
- While the pages run from the sources, `http/assets.js` sends every file that is not named by its content (`src/client/`, `src/shared/`, the catalogues and pictures of `public/`) with `Cache-Control: no-cache`: the browser asks again at each use and gets a 304 when nothing changed, so a change shows on a plain reload. With an hour of cache (what it sent until 2026-10-11) a browser that had visited the site kept the old stylesheet and the old pages after a fix, a plain reload did not refresh them, and not even a hard reload refreshed the pages loaded on demand (`import()` after the load event): a fix looked as if it had not worked. Once a bundle is built the sources keep the hour (the pages read the bundle), the fonts and icons a year. `src/server/platform/http/source-caching.test.js` holds both policies.
- The Dockerfile builds in a first stage (it copies `src/client/`, `src/shared/`, `src/public/`, `build.mjs` **and `src/server/platform/http/first-paint.js`**: the build plans the first-paint CSS of each view with the module the server uses, and an image that lacks it fails at `node scripts/build/build.mjs` with `ERR_MODULE_NOT_FOUND`); the final image holds `src/` (without its tests, `src/testing/` and `src/translations/`, see `.dockerignore`), `dist/` and `scripts/accounts/`.

## Performance and several instances

`docs/PERFORMANCE.md` is the ledger: the tools, the numbers, what each item of the checklist found and did. The rules that came out of it:

- A list is read through the person's own rows (`UNION` of the owner and the member index), never `owner = ? OR member IS NOT NULL` over a join: that form reads every row of the table.
- A request must cost the same number of SQL statements for a busy and for a quiet person (`scripts/performance/api-probe.mjs` reports a statement repeated three times in one request; `src/testing/sql-recorder.js` pins a count in a test).
- `/api` and `/auth` are `no-store` unless a route says otherwise through `http/cache-control.js`, and only for a good answer; the error handler makes every error `no-store`.
- Everything a timer runs that asks a remote service takes `store.runExclusive(name, …)`; in-memory caches are per instance, so their lifetime is short (30 s) and a write clears the instance that took it; rate limits are per instance.
- `GET /api/health` is readiness (MySQL answers, and 503 once the instance drains: `SHUTDOWN_DRAIN_SECONDS`); `GET /api/health/live` is liveness.

## Translations

English text is the key. `npm run i18n` collects every translatable string (`scripts/i18n/keys.mjs`), merges `src/translations/*.txt` and writes `src/public/locales/<code>.js`. Fifteen languages ship, Arabic is right-to-left; the layout uses logical CSS properties so it mirrors by itself. The server and the client read the same files.

These files are the words of the **interface**. What the **staff** writes (names of stats, items, notes, builds, situations…) is not in them: it lives in the database, is kept as typed, and is translated by the `translations` feature (see the server section) into the same fifteen languages. A text is keyed by its own content (a SHA-256), so one text used in many places is translated once.

## Tests

- `npm test` runs every `*.test.js` of `src/` and `scripts/` with `node:test`, each next to the code it checks. They need MySQL (`docker compose up -d mysql`); when it is unreachable the database tests skip, they do not fail.
- The `*.e2e.mjs` files are Playwright scripts, each next to its feature (`node src/client/app.e2e.mjs`). Each starts its own server on a free port with its own database. `npm run test:e2e` (`src/testing/run-e2e.mjs`) runs them all, keeps going after a failure and ends with the list of what failed; give it names to run only those. `screenshots`, `export-preview` and `video-frame` (in `scripts/dev/`) are review helpers that write pictures, not tests.
- `src/client/design.test.js` also guards the stylesheets: every `@import` resolves and no sheet is left unimported, every `var(--x)` is defined, every animation has its `@keyframes`, palette contrast, no inline `style` attributes, a class has its base rule in one sheet only, and a page sheet only styles bare classes (`.name { … }`) that the features of its page write (the table `PAGE_FEATURES`: a rule for a bare class reaches every element of the app that carries it).
- `src/client/styles/layout-lint.e2e.mjs` runs the measures of `src/testing/layout-lint.js` in the page on the 48 pages of the demonstration world, in both themes, on a phone (390 px) and on a desktop (1440 px): nothing that runs out of the screen or of its box, text cut without an ellipsis, boxes of the flow lying over each other, a squashed picture, a target under 24 px on a phone, a text under 11 px, an empty framed box, a page that scrolls sideways. What is on purpose (the `i` of a badge, one-pixel texts for the screen readers, table cells, stacks of avatars) is excluded in the measure with its reason, so a failure is a defect to fix, not a line to add to a list. It does not replace looking at the pages (the contact sheets of `scripts/dev/screenshots.mjs`); it keeps what was found from coming back.
- Four browser tests walk the whole demonstration world (`scripts/dev/demo-data.mjs`, `demoPages()`: 48 pages as a visitor, a captain and an administrator): `src/client/styles/contrast.e2e.mjs` (the text of every page reaches WCAG AA in both themes, the headings go down one level at a time, the lane logos sit inside their chips), `src/client/xss-crawl.e2e.mjs` (markup written straight into the database stays text on every page), `src/client/styles/first-paint.e2e.mjs` (the first screen of a page the server draws looks the same with its own sheets as with the whole stylesheet) and `src/client/styles/hit-test.e2e.mjs` (every visible control is what a pointer finds at its centre, on a desktop and a phone, with motion and with reduced motion: it catches a control that something covers, which a click crawl cannot tell from a control that does nothing). Each proves its detector on a page built for the purpose before it judges the site, so that a silent run cannot pass for a clean one.
- Two lessons of the layout that these tests hold. A finished entrance animation (`.rise`, fill mode `both`) leaves an identity `transform` and a stacking context on its element: whatever is `position: fixed` inside it is placed against it, not against the screen, and whatever has a `z-index` inside it is stacked in it. With reduced motion the animation does not run, so the stacking changes: a fixed sheet must not live under a `.rise`, and a `z-index` that matters must come with `isolation: isolate`. And a box that scrolls must not centre its lines (`align-content: center`): the overflow is shared between both ends and the part above cannot be reached.
- `src/server/route-access.test.js` freezes who can reach which of the routes declared under `src/server/features` (open, account, editor, admin, member, login-flow): each is called as a visitor, a person, a contributor and an administrator (`src/testing/route-access.js`; `node scripts/dev/route-matrix.mjs` prints the matrix). **A new route fails it until it is classified.**
- `src/testing/nav.js` (`goNav`, `openHeroTab`) and `src/testing/text.js` (`textOf`): the top bar keeps its entries in groups that open on a click, and CSS writes titles, buttons and tabs in capitals, so a browser test clicks through `goNav` and compares text with `textContent` (`innerText` follows the capitals).
- `scripts/database/drop-test-databases.mjs` removes the throw-away databases (`hok_test_` + 12 hexadecimal digits) that a killed test or script leaves behind. It lists first and drops only with `--apply`, never a database that has a connection on it nor one younger than ten minutes; the rule that decides is a pure function, `judge`, with its own test (`scripts/database/test-databases.test.js`).
- `src/testing/test-app.js` builds a full app around a clean database; `src/testing/sources.js` reads the sources (resolving CSS `@import`s) for the tests that check them.

## Code conventions

- Prettier (`.prettierrc.json`, 100 columns) and ESLint (`eslint.config.js`, braces always) decide the format; run `npx prettier --write .` and `npx eslint .`.
- Comments are in English and say why, not what.
- One module, one job, and a size that is **enforced**: `src/architecture.test.js` fails when a JavaScript file is over 400 lines, a function over 120 lines or a stylesheet over 600 lines. The cases that are still over are listed, with their reason and at their exact size, in `src/architecture-limits.json`; a listed size can only go down. How a page is cut into files (pure markup files, a shared `view`, `bindTo`) is in [PAGE-ANATOMY.md](PAGE-ANATOMY.md); the recipes to change something (a text, a colour, a button, a page, a route, a column) are in [HOW-TO.md](HOW-TO.md); every folder of `features/` has a `README.md` that lists its files.
- Every user-facing text goes through `t()` (client) or the error templates (server). Never concatenate translated fragments.
- Migrations are additive and numbered; an applied migration is never edited.

## Where things are

Everything the application runs is under `src/` (`server`, `client`, `shared`, `public`, `translations`), with its tests next to it and what they share in `src/testing/`; the commands are in `scripts/`. Older locations (the folders of the first versions, the interactive mock-up and the design notes) are not in the repository any more: they are in the git history up to commit `30ba879`, and the design material was moved out of the repository on 2026-10-18.
