# Security

## Accounts and sign-in

| Topic               | What is done                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Accounts            | Real accounts in MySQL: email + password (`users.login_email` unique, normalised), or Google. Guests (no account) own their data through a random 256-bit cookie until they sign in.                                                                                                                                                                                                              |
| Password storage    | **scrypt** (N=2^17, r=8, p=1, 128-bit salt, 64-byte key) from Node's own crypto (no native dependency), parameters stored with the hash and upgraded at the next sign-in. Optional server-side **pepper** (`PASSWORD_PEPPER`, HMAC-SHA-256 before hashing). Hashing concurrency is bounded so a login flood cannot starve the server.                                                             |
| Password policy     | 12–128 characters, no common passwords/keyboard runs, must not contain the email name or the display name, minimum variety. NFKC-normalised.                                                                                                                                                                                                                                                      |
| **MFA (mandatory)** | Every account needs a **TOTP authenticator** (RFC 6238: SHA-1, 6 digits, 30 s, ±1 step drift). No session exists until password (or Google) **and** the code are verified. Accounts are enrolled right after registration; Google accounts too.                                                                                                                                                   |
| TOTP seeds          | Encrypted at rest with **AES-256-GCM**, key outside the database (`MFA_ENCRYPTION_KEY`), authenticated with the user id (a seed cannot be moved to another account).                                                                                                                                                                                                                              |
| Replay              | Each accepted time step is stored (compare-and-set): a code works once, even with parallel requests.                                                                                                                                                                                                                                                                                              |
| Recovery codes      | 10 single-use codes (≈50 bits each), stored as SHA-256 hashes, shown once, regenerated with a fresh authenticator code.                                                                                                                                                                                                                                                                           |
| Brute force         | Per-IP limits on login/register/MFA; per-challenge limit (5 codes); per-account **progressive lock** (15 min after 5 failures, doubling, 24 h max). The lock is not revealed: a locked account answers like a wrong password.                                                                                                                                                                     |
| Enumeration         | Unknown email and wrong password give the same answer and take the same time (dummy hash).                                                                                                                                                                                                                                                                                                        |
| Sessions            | 256-bit random token, SHA-256 hashed in the database, `HttpOnly`, `SameSite=Lax`, `Secure` + `__Host-` prefix in production, **rotated at every sign-in**, 14-day sliding / 30-day absolute. Password change closes the other sessions; "sign out everywhere"; logout deletes the server-side session. Migration 007 closed every pre-existing session so everybody re-authenticated through MFA. |
| Step-up             | Changing the password or regenerating recovery codes needs a **fresh** authenticator code (and the current password).                                                                                                                                                                                                                                                                             |
| Journal             | `auth_events`: sign-ins, failures, locks, MFA changes (no secrets), 180 days, visible to the user in **Account**.                                                                                                                                                                                                                                                                                 |
| Admin               | `ADMIN_EMAILS` applies only to **verified** emails: Google, or accounts created by the server owner with `scripts/account.js create`. Public registration of an admin address is refused.                                                                                                                                                                                                         |
| Google              | OAuth with PKCE (S256) and `state`; only the **first factor**: the authenticator code is still required. A Google account never merges with a password account of the same email (separate identities).                                                                                                                                                                                           |
| Lost device         | Recovery code; if everything is lost, the server owner runs `scripts/account.js reset-mfa --email …` (password still required afterwards).                                                                                                                                                                                                                                                        |

## Web application

- **CSP**: `default-src 'self'`, `script-src 'self'`, `style-src 'self'` (no inline script or style, no `unsafe-*`), images limited to Camp/Google/`data:`, media limited to Camp, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`. The only inline code is what the server itself writes, each allowed by its SHA-256: the constant boot script, and one `<style>` (the critical CSS, plus for a page the server draws the sheets of its first screen, so each such page sends the CSP with its own hash). Also `nosniff`, referrer and permissions policies, COOP/CORP, HSTS in production, no `X-Powered-By`, `Cache-Control: no-store` on APIs and private pages.
- **CSRF**: `SameSite=Lax` + refusal of cross-site `Sec-Fetch-Site` and foreign `Origin` on every write.
- **Authorization**: every query filters by owner or membership; 404 for everything else; roles for online series; strict validation of every body (types, sizes, ids); imports rebuild ids/owner/status server-side.
- **SQL**: every value goes through a `?` placeholder. The 540 calls to `query`/`execute` of `src/server/` and `scripts/` were read with a parser (the 72 that build their text from pieces only interpolate constants, column lists written in the code, or a value taken from an allow-list: `SERIES_SORTS`, `parseQueryChoice`, `Object.hasOwn` before a lookup keyed by the request); a new call that interpolates is a reason to look twice.
- **Rate limits** on auth, creation, join, draft actions, import, export, sync and writes; `TRUST_PROXY` configurable.
- **Caching**: everything under `/api` and `/auth` is `no-store` (private data is never stored by a browser or a proxy); the only exceptions are set route by route after the answer is known to be good: public data that is the same for everybody (the catalogue, the popularity pages; they never carry a session cookie, and no `Vary`) and the hero list and backgrounds, which depend on the language and are stored by the browser only (`private, no-cache`); every error response is forced to `no-store`. Pictures and scripts carry no `Vary` on the cookie. Rate limits are kept in memory per instance: behind a load balancer send a client to the same instance or accept limits N times looser (`docs/PERFORMANCE.md`).
- **Editors**: the pages that write what every visitor sees (recommended builds, combos, official ratings) need `isEditor` (administrator, or the `contributor` label): `requireEditor` on `/api/builds`, `/api/combos`, `/api/official-tiers`. The label is read at every request, so removing it takes effect at once. The administration (`/api/admin/*`) stays administrators only.
- **Shared spaces** (`/space/shared#<token>`): the token is 192 random bits (`sp_` + base64url), only its SHA-256 is stored (`space_links.token_hash`), it is returned once when the link is made and never listed again. It sits after the `#` of the address, so no server, proxy or log receives it; the page sends it in the body of `POST /api/space/open`. An unknown, removed or expired token gives the same 404. A link shares only the parts its owner ticked, read only, never the e-mail address nor the answers to the training situations; the page creates no session or guest identity. 20 links per account at most; a link can be removed at any time; removing the account removes its links (foreign keys). The page `/space/shared` is **indexable on purpose** (revision 42: a Lighthouse SEO of 100 on every page): a search engine receives the same empty page as everybody, because the secret never reaches a server; it stays out of the sitemap, and a drawn frame of it is never kept by a shared cache (`no-store`). To go back to `noindex`, set `index: false` on that route in `src/shared/routes.js` and turn the assertion of `space.e2e.mjs` and of `pages.test.js` round.
- **Conditions on a hero** (the "only for melee heroes", "level 8 or more" of an item): they are **data, never code**. The page builds a small tree (`all`/`any`, at most three levels, 12 conditions, 20 heroes per list), the server reads it back with its own parser (`parseWhen`: every field is checked, the stat, tag and hero must exist, a stored option must be an option of that stat) and stores what it understood, not what was sent. The browser and the server walk it with the same pure function; nothing is ever passed to `eval`, `Function` or a template. The answer can be _yes_, _no_ or _cannot be known_, and an unknown answer is never turned into _no_ (a value that depends on it is not counted and is shown as unchecked). A stat, an option or a tag that a condition or a line uses cannot be deleted or change kind (409).
- **Automatic translation** (off by default, `TRANSLATION_PROVIDER`): when it is on, **only the texts the staff wrote** go to the service you chose (a stat name, an item description, a note…), one batch at a time, together with the list of languages. Nothing about people goes: no account, e-mail, team, tier list, notebook or message, and the texts of players are never translated. Texts of an unpublished training situation are not collected, and neither are texts nobody uses any more. The key is read from the environment only (`TRANSLATION_API_KEY`): it is never written to the logs, never returned by an API, and the start-up check names the missing setting, not a value; a request never logs its headers. The Claude prompt says that the texts are data and that nothing in them is an order, and **what comes back is not trusted anyway**: it is read as JSON, each translation is cleaned (no markup, no control character), must keep every number of its text, must not be empty or much longer than the text, and is stored and shown like any other text (escaped by every page). A translation an administrator wrote by hand is never overwritten, and is cleaned the same way. What is sent is bounded twice: by the quota that the provider itself reports for the account (DeepL's `GET /v2/usage`: the translator stops at 90 % of it, and a 456 pauses it until the period ends or tomorrow instead of trying again), and, when the owner wrote one or the provider cannot report a quota, by a daily number of characters (`TRANSLATION_DAILY_CHARS`). A language is translated only once somebody asked for it, so what a visitor can make the site spend is bounded by the fifteen languages of the site, each translated once (a visitor cannot ask for anything else: the language is checked against the list). The key is read from `DEEPL_API_KEY` (or `TRANSLATION_API_KEY`) in the environment only; `npm run translations:check` reads the quota and the languages (it costs nothing) and never prints the key. A service that refuses the key stops the translator until the key changes. Only one process translates at a time (`GET_LOCK`). The administrators' routes (`/api/admin/translations/*`) are administrators only; the dictionary route is public and serves only source/translation pairs of the texts the site already shows to everybody. Whatever is sent to a service is subject to its own terms: **choose `libretranslate` on a server of yours if nothing may leave it**.
- **Sorting and importing the catalogue**: sorting items in bulk (`POST /api/admin/catalog/items/bulk`) is for administrators only (the `/api/admin/*` prefix), takes at most 300 distinct items, checks every field against the lists (a slot is not a category and the reverse), is one transaction (all of them or none) and refuses to move an item out of the slot that a recommended build has it in. The importer of pictures (`scripts/catalog/import-images.mjs`) is run by a person who has access to the database: it reads the database settings from the environment and never prints them, shows what it would do before doing anything (`--apply` is needed), goes through the same parsers as the page, writes only entries and their pictures (no stat, price or text invented), skips a name that is already there, and writes a manifest to `backups/` so that `--undo` can take it back. A picture is decoded and re-encoded by the server (the original is never stored or served), at most 3 MB and 40 million pixels; the size a page asks for (`?w=`) is one of three values, anything else gives the picture itself.
- **Reflex runs**: the score and the duration of a run are sent by the browser and cannot be proved, so the server only refuses what no honest run gives (a score out of the range of the exercise, a run shorter than a person can play or longer than half an hour, more than 600 runs a day). A run only counts for the player who sent it.
- **Training of a team**: the goals about reflexes and about heroes are written by the owner, the managers and the coaches only (`canAssignTraining`); every other member of the team reads, and a player only ever gets **their own line** (`GET /api/training/assigned`, the table of the team page). The **ranking** is closed to the players until the staff opens it (`team_training_settings.leaderboard`; a player who asks anyway gets a 403) and lists only the people who are asked to train, by name and tag, never an e-mail address. What a review schedule holds (`combo_reviews`) is the player's own and goes away with the account or the combo (foreign keys).
- **Video reviews** (notebook notes with a link): the link is kept only if it is an `https://` address of a site, written without a login, without a port, without spaces or control characters, not `localhost` and not a numeric address, 500 characters at most (`src/shared/vod-model.js`, the same rules in the browser and on the server). **The server never fetches it**: no request goes out because of a link a person typed. The page checks the address again before it draws a link (what is not a fine address is shown as plain text, so a `javascript:` address that got into the database would still not be a link) and opens it with `target="_blank"` and `rel="noopener noreferrer nofollow ugc"`. The moments are text, escaped like every other text. **A shared space shows the link and the moments to whoever has the space link**, as it shows the rest of the notebook: the person ticks the parts a link shows when they create it (the training sheet is one of three).
- **API keys and the public API** (`/api/v1`, see [API.md](API.md)): a key is 256 random bits (`hok_` + 43 characters), only its SHA-256 is stored (a unique index on the hash; no salt or slow hash is needed at that entropy) with its first 10 characters to recognise it; the secret is in the answer that creates it and nowhere else. A key **only reads** (the gateway answers 405 to anything but GET, HEAD and OPTIONS), holds scopes, expires (90 days by default), is revoked at once, and is **never an administrator or an editor** whatever its owner is on the site. The addresses a key may call are an **allow-list** (`features/api-keys/endpoints.js`): everything under `/api/admin`, sign-in, account security, the staff's own lists and every file download are not on it; the key is read from the `Authorization` header only (never the address, which would end up in logs and in the history of a browser), cookies are not read on these addresses, and keys are made, listed and revoked with the browser session only (a leaked key cannot make another). An unknown, revoked or expired key gets the same answer. Every refusal is counted against the address of the caller (60 in 15 minutes, then 429) _after_ the lookup, so a neighbour behind the same address cannot take somebody's access away; a key's reads are limited per key (120 a minute), not per address. CORS is open for reading without credentials.
- **Who can reach which route** is frozen in `src/server/route-access.test.js`: every route declared under `src/server/features` is called as a visitor, an ordinary person, a contributor and an administrator and must answer as its class says (open, account, editor, admin, member, login-flow). **A new route fails the test until it is classified.** Every `/api/admin` route is for administrators only; an ordinary person gets 403 and a visitor 401 whatever the route's id or body.
- **Series shared with a team**: only the creator of a series who leads the team (owner, manager or coach) can put it on the team; every member then reads it as a _viewer_ (the series policy refuses every write to a viewer); taking it off, or leaving the team, ends the access at once; a series is on 5 teams at most.
- **Image proxy** (`/media/img`): the hosts are **exact names** (`camp.honorofkings.com`, `res.sgameglobal.com` and the one video account of Camp), never a suffix of a cloud provider's domain: anybody can open a storage bucket under such a domain, and the proxy would fetch and keep what they put there. No redirect is followed, only PNG/JPEG/WebP/GIF, 30 MB and 60 million pixels at most, 3 downloads at once with at most 64 waiting (past that it answers at once that it is busy and remembers nothing), the addresses that failed are remembered for 5 minutes but only 2000 of them, and the pictures kept on disk are pruned to a 512 MB budget (the oldest first; only its own files, never the other files of the folder).
- **Output**: all user/source data is escaped in templates; typed JSON errors, details only in the logs, logs redact cookies/tokens/secrets. Two browser tests hold this: `src/client/xss.e2e.mjs` (hostile strings sent through the API, which validates them) and `src/client/xss-crawl.e2e.mjs`, which goes round the validation: it builds the demonstration world, writes a payload (`"><img src=x onerror=…><u id=__xss>`) straight into every free-text column of the database (names, notes, descriptions, titles, messages, bios, labels) and into the words of the JSON of series, tier lists, notes and scenarios, then opens the 33 pages of the site as a visitor, a captain and an administrator, tabs included, and fails on any injected element, any `on…` attribute or any script that ran (the policy would stop the handler, so the test looks for the markup itself; a probe proves the detector sees injected markup, and the test requires the payload to be on screen, as text, on at least 15 pages).
- **Uploads**: only PDF/PNG generated by this site, type read from the bytes, 12 MB limit, decompression-bomb limit, same validation as any import.
- **PDF export**: Chromium with JavaScript off and the network blocked, portraits fetched only from `camp.honorofkings.com` into a local cache.
- **Production refuses to start** with default/short DB passwords, without `MFA_ENCRYPTION_KEY`, with a weak scrypt cost, with insecure cookies or a non-https callback, or with a database that is not on this machine or a private network (a host name with a dot that is not a private address) and no `DB_SSL=true`. With TLS the certificate of the database server is always verified (`rejectUnauthorized`, TLS 1.3 only; `DB_SSL_CA` adds the authority of a provider the system does not know); the connection that holds the advisory locks is encrypted the same way. A hosted database should also have its IP allow-list narrowed when the provider offers one, and a user of its own with the rights on this one schema only.
- **Container**: non-root, read-only filesystem, all capabilities dropped, `no-new-privileges`, memory/PID limits, healthcheck, graceful shutdown.

## Operating it

```powershell
# a key for the authenticator seeds (keep it in a secret store; losing it means every user re-enrols)
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"     # -> MFA_ENCRYPTION_KEY
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"     # -> PASSWORD_PEPPER (optional, never change it afterwards)
# create the first administrator (password from stdin, never on the command line)
$env:HOK_PASSWORD = "a long passphrase"; node --env-file=.env scripts\account.js create --email you@example.com --name "You"
node --env-file=.env scripts\account.js reset-mfa --email someone@example.com
node --env-file=.env scripts\account.js unlock   --email someone@example.com
```

## Testing it

Nothing here needs real data: every instance below runs on a throw-away database.

```powershell
npm audit                                                  # dependencies: 0 vulnerabilities (shipped and development)
node --test src/server/route-access.test.js "src/server/platform/http/*.test.js"   # who may call what, headers, CSRF, cookies, rate limits, uploads
node scripts/security/serve-production-like.mjs            # this code, configured as production; prints READY http://127.0.0.1:<port>
$env:PROBE_FORWARDED_PROTO = "https"                       # the probe comes through the proxy that ends TLS, as every visitor does
node scripts/security/vulnerability-probe.mjs http://127.0.0.1:<port>
node scripts/dev/consignes-audit.mjs <address of node scripts/performance/serve-built.mjs>   # the owner's two lists
```

The probe (`scripts/security/probe/`, one file per group of checks) is a black box that only sends requests a visitor can send: the security headers and the content policy, plain http sent to https (308) and HSTS, files that must not be served and path traversal, the admin and account API closed to a visitor (401 or 403, never 404: a path that does not exist proves nothing), writes from another origin, `?next=` redirects, reflected input, SQL-injection-style input and hostile bodies (invalid JSON, prototype pollution, deep nesting, 3 MB), the rate limit of the login (429), the same answer whether an email has an account or not, and a forged `Host`. Run against a test instance (`startTestServer`) the limits are off on purpose: say so with `RATE_LIMIT_DISABLED=true`, or use the production-like instance, where they are on.

Result of 2026-10-24, on the code after the refactor: 107 of 107 checks held in the production configuration, 105 of 105 on the test instance; `npm audit` 0; the owner's list `consignes-audit` 25 of 25 (the two items of Search Console and links are the owner's). The first run found one real defect, fixed: in production the page renderer asks the server over plain http from inside, and `enforceHttps` sent that request to https, so it failed and the server never drew the first screen (the page was then drawn by the browser, slower). The renderer is now let in by the random secret it keeps (`x-hok-prerender`, `src/server/platform/http/https-redirect.test.js`); anybody else is still sent to https.

Result of 2026-10-30, before the move to Hetzner (`deploy/HETZNER.md`): 107 of 107 again in the production configuration, `npm audit` 0 (shipped and development). A second pass, signed in with two real accounts on the production-like instance (sign-up, authenticator, then attacks), found nothing to fix: the session, challenge and sign-out cookies are `__Host-`, `Secure`, `HttpOnly` and `SameSite`; a tampered cookie and a cookie copied before sign-out both give 401; extra fields (`role`, `isAdmin`, `verified`) on the profile change nothing; a stranger gets 403/404 on every write to another person's team; markup in a team name is refused; out-of-range and repeated query parameters (`pageSize=1000000`, `page=1e20`, `q[]`, `pageSize[$gt]`) answer cleanly and bounded; no error shows a stack, a path or a SQL message; `TRACE` is not echoed; a 90 KB address and a 70 KB header are refused; a `text/plain` body is not read as JSON; a signed-in write from another origin is refused; an SVG sent as a PNG, an SVG avatar and a GIF/JavaScript polyglot are refused. Reading the code: every request the server makes leaves for a fixed list of hosts (Google, Discord, the Camp media hosts, the translation provider) with redirects refused, so no address chosen by a visitor is ever fetched; uploaded pictures are decoded by libvips with every loader but PNG, JPEG, WebP and GIF blocked. The production stack publishes only Caddy (80, 443); the site listens on the machine itself only and MySQL is not published (`docker compose config` checked); an encrypted backup was restored into a throw-away MySQL with the same counts (`deploy/restore-test.sh`).

## Known limits (honest list)

- The registration form says when an email address is already in use (`email_taken`), and an account is locked for a while after repeated wrong passwords, which anybody who knows the address can provoke: the two usual costs of having no mail service to confirm by. The `auth` and `login` limiters (30 and 12 per 15 minutes per address) bound both.
- No email verification or password reset by email (there is no mail service): password-account emails are unverified, which is why they can never be administrators and why a lost password needs the owner (`account.js`).
- Authenticator apps are phishable by a real-time proxy; passkeys (WebAuthn) would fix that and are the natural next step.
- TOTP uses SHA-1 as the standard apps expect (HMAC-SHA-1 is not affected by SHA-1 collisions).
- Rate limits are per process (a single instance); behind several instances use a shared store.
- The public API is read-only on purpose; writing through it would need its own review (what a key may change, a second confirmation for the dangerous ones).
- A guest identity can be made by anyone who creates a local series (that is the product: no account to try it); the creation limit (60 an hour per address) and the quotas bound it, and old guest sessions expire (a year at most).
- In production a request that arrives over plain http (the proxy says so with `X-Forwarded-Proto`, `TRUST_PROXY` set) is redirected to https with a 308 (`enforceHttps`), except `/api/health` and the page renderer (it asks the server itself over http and proves who it is with a random secret that never leaves the process); HSTS follows. Without `TRUST_PROXY` behind a proxy every request looks like http: set it.
